# Build rulings (v1)

Decisions the build controller took on the owner's behalf while building v1 with subagents (Oct 16–17, 2026), in the order they were made. Each line says what was decided, why, and what it costs if wrong. Implementation-level judgment calls are in docs/decisions.md.

## Rulings

- Ruling 1: all subagents run on Opus 5.5 (model "opus") — user instruction overrides the skill's cheaper-model guidance — cost: higher token spend.
- Ruling 2: no pause for plan approval — user said "bouw het maar in fases" — cost: rework if the plan misreads intent.
- Ruling 3: build on branch build/v1 in place, no worktree — fresh repo, nothing else in flight — cost: none.
- Ruling 4: scope = planning phases 1–5 (version 1, version 2, sharing); version 3 (slow pages, uptime, API/MCP) and session replay out of scope — matches the spec's five phases — cost: none.
- Ruling 5: never store IP addresses at all (spec allows drop or truncate) — stricter privacy — cost: no country unless the SDK sends geo.
- Ruling 6: BASE_URL must be the root of a host — DSN paths stay simple — cost: no subpath hosting.
- Ruling 7: module and binary named `monitor`; UI name `[Tool name]` in one place — name undecided — cost: a rename later.
- Ruling 8: admin "reset password" for a member = one-time reset link — no admin-chosen passwords — cost: small UX difference from the spec wording.
- Ruling 9: spike threshold = multiplier (default 5×) over the previous 7 days' hourly average, minimum 10 errors, 6 h cooldown — spec only says "the threshold" — cost: retune.
- Ruling 10: email notifications go to all users with access to the project — spec names no recipients — cost: no per-user opt-out.
- Ruling 11: notification delivery is in-memory with retries, not a durable outbox — YAGNI — cost: notifications lost on a restart mid-delivery.
- Ruling 12: a page view's duration also closes on the next $pageview in the same session (SPA navigation) — otherwise SPAs have no durations — cost: diverges from a strict "pageleave only" reading.
- Ruling 13: unique visitors via mergeable HyperLogLog sketches in hourly_stats — uniques cannot be summed across hours — cost: ~1–2 % error.
- Ruling 14: route patterns apply to new data only — cost: historic data stays ungrouped after a pattern change.
- Ruling 15: source maps symbolicated at ingest when present, read-time fallback — stable grouping — cost: more ingest work.
- Ruling 16: documentation for other self-hosters in English (UI is English) — cost: Dutch readers.
- Ruling 17: restore is staged and applied at next start — no hot swap of the live DB — cost: needs a restart.
- Ruling 18: implementation tables beyond the spec's eleven (sessions, password_resets, alert_state, settings, api_tokens, event_hourly) — spec lists the domain tables only — cost: none.
- Ruling 19: Task 4 owns the issues `route` filter (column from T1, filled from T7); Task 8 only links to it — duplicate ownership in plan — cost: none.
- Ruling 20: perf targets (writer ≥ 5 000 events/s, aggregation < 60 s, page queries < 300 ms on 1 M pageviews) chosen by the controller — spec gives no numbers — cost: retune.
- Ruling 21: commits use the user's git identity with the Co-Authored-By trailer; nothing is pushed — cost: none.
- Ruling 23: the "main" exception is the LAST entry of exception.values (outermost, newest — Sentry's order is oldest→newest), used for title, message, culprit and fingerprint — plan text said "innermost", but the design shows `QueryException` (Laravel's outer wrapper of PDOException) as the title and Sentry shows the last value — cost if wrong: one-line flip back.
- Ruling 24: fixtures may be sanitized (scratchpad path → neutral path, kernel/host strings → generic) and re-compressed; they must keep the real SDK structure, not byte identity — the repo may be published — cost: none.
- Ruling 25: UI shows short exception type (after last `\` or `.`), full class name on detail + tooltip; API returns full type — design shows `QueryException` — cost: none.
- Ruling 26: when the main exception's mechanism type is `onunhandledrejection`, the issue title shown is "Unhandled rejection" (as in Issues.png); fingerprint unchanged — design match — cost: one label rule. Confirmed as a real gap → fix loop.
- Ruling 27: browser (javascript) culprit = frame URL path without origin, query and leading slash (e.g. `assets/main.js:21`; original source path once Task 10 symbolicates, like `resources/js/cart.js:142` in the design); PHP keeps basename (`CheckoutController.php:88`, as designed) — design match — cost: none. Confirmed as a real gap → fix loop.
- Ruling 28: "Newest issues" = open issues first seen in the last 24 h, ordered by last_seen DESC — the design's times are last-seen times — cost: an old-but-busy new issue can sit above a newer one. (decisions.md:241 claim about "the design's rows" is wrong → carried as minor.)
- Ruling 29: "See all issues" opens the issues page of the newest row's project — the spec has no cross-project issue list — cost: one extra click for other projects.
- Ruling 30: severity upgrades by controller (security): (a) pending invites created by an admin survive that admin's removal/demotion → Important (privilege persistence); (b) per-client throttle key: XFF trusted from any private peer and left-most entry used / IPv6 per /128 → folded into the Critical fix (use the right-most untrusted XFF entry, bucket IPv6 by /64); (c) unbounded limiter keys → folded into the Critical fix (hash email keys, hard key cap) — same code as the Critical — cost: a slightly larger fix round.
- Ruling 31: per-address throttle keeps two stores — keys for existing accounts are never evicted inside the window (bounded by the number of users); keys for unknown addresses live in a capped, evictable store; both enforce the same 5 per 15 min so the responses do not reveal whether an account exists — closes the flood bypass without an enumeration oracle or a fail-closed DoS — cost: a user lookup before the throttle step.
- Ruling 32 (replaces Ruling 31): silent per-account lockout. The per-address limit applies only to existing accounts and never answers 429: a locked account answers exactly like a wrong password (same 401 body, same timing via the dummy hash), even for the correct password. Unknown addresses are not tracked per address at all (no store, no eviction). The per-client limit (20/15 min) keeps answering 429 (it counts all tries from a client regardless of address, so it reveals nothing). Forgot-password: per-account limit silently stops sending mail after 5 per 15 min; the answer is always the same. Account page (signed in, own account): may keep answering 429. The 401 copy tells users that 5 wrong tries pause sign-in for 15 minutes and points to reset — bounded memory (keys ≤ accounts), no flood bypass, no enumeration — cost: a locked-out user with the right password sees the generic message until the window passes (mitigated by the copy and by reset/forget clearing the lock). Overrides the brief's "5 failures per email → 429".
- Ruling 33: alert settings, the project Slack webhook and "Send test message" are admin-only to change (members may view, webhook masked); webhook URLs must be https — the spec says admins manage settings, and a member-set webhook lets members make the server POST to arbitrary URLs — cost: members cannot tune alerts themselves.
- Ruling 34: /health answers 503 only when the tool cannot work (database check fails, or disk free < 1 % or < 256 MiB, where writes start failing); below 10 % or 1 GiB it answers 200 with status "degraded" and the failing check, and raises the admin alert — a low-but-working disk must not make Docker/load balancers mark the service down — cost: monitors that only read the status code see "degraded" as healthy.
- Ruling 35: members get 404 from the alert change routes (existing adminOnly convention); the UI never offers the action to members (read-only page, masked webhook, one line "Only admins can change alerts.") — consistency with the 404 convention — cost: none.
- Ruling 36: https-only webhooks in production; a dev/test-only env flag `DEV_ALLOW_HTTP_WEBHOOKS=true` allows http for local fakes (e2e, container check), logged as a warning at startup and documented as never-for-production — Go on macOS cannot be pointed at a test CA easily — cost: one more env flag that could be misused.
- Ruling 37: PostHog keeps its own per-project rate-limit window with the same number as Sentry — a burst of page traffic must not starve error ingest — cost: a project's total budget is twice the configured number.
- Ruling 38: stored paths and URLs are masked for token-like segments (`:uuid`, `:hash`, `:token`; digits and slugs kept) before storage — in pageviews.path AND in error_events.url — Laravel reset routes would otherwise store live reset tokens and Task 8 shows raw-path previews — cost: raw-path previews show masks.
- Ruling 39: ⚠️ items accepted — Pages totals take visitors from PageStats (no visitors field on PageviewTotals); the `tz` query parameter; the admin-only route preview reading raw pageviews/error_events (the brief asks for raw paths); no backfill of pre-Ruling-38 rows (no production data exists yet) — cost: none now.
- Ruling 40: the issues `release` filter means "has events in that release"; the stats-strip link's title must say so ("See issues with events in this release"), not "First seen in X…" — cost: none.
- Ruling 41: Sentry event times are drift-corrected to the server clock like PostHog's (timestamp + (received − envelope sent_at) when sent_at is present; otherwise the existing clamp) and stored that way, so the journey and activity compare one clock — cost: stored error timestamps differ slightly from the client's own clock.
- Ruling 42: the corrected Sentry time is capped at the receive time (an error cannot happen after it arrived) — sentry-php's whole-second sent_at otherwise puts PHP errors up to 1 s late and lets the error page's own page view into the journey — cost: none.
- Ruling 43: the Sentry-compatible `/api/0/...` upload routes answer 401 (bad token) and 403 (token lacks the project or unknown slug, identical text) as the brief says — Sentry clients expect them and the identical text leaks nothing — the dashboard's 404 convention stays for `/ui/api/` — cost: none.
- Ruling 44: severity upgrades by controller — (a) the writer's 200 ms/1 s/5 s retries drop acknowledged events during a routine Postgres restart/failover → Important: keep retrying with capped backoff (up to ~2 min) while the database is unreachable and let the bounded queue answer 429 meanwhile; (b) retention as deadlock victim skips the whole project for 24 h → fold into this round: retry the batch on SQLSTATE 40P01 (and 40001), never skip the remaining kinds — cost: a slightly larger fix round.
- Ruling 45: Task 12 is split into two sequential dispatches to keep each reviewable — 12a: brief Steps 1–2 (backup/restore, delete user data, their UI) + the code carry-over items; 12b: brief Steps 3–5 (docs, CI, multi-arch image, ten-minute test) + the docs carry-over items — cost: one extra review.
- Ruling 46: severity upgrades (restore is security/integrity-critical) — fold into this round: compare the backup's schema with the binary's reference schema (sqlite_master of migrations 1..v applied in memory) and open restored/validated files with `_defensive=1`; close the WAL crash window in the swap (always move a leftover non-empty -wal into backups/ and remove -shm before putting the pending file in place) with a WAL-folding test; use `quick_check` + schema checks at startup instead of a full integrity_check (the full check already ran when staged) — cost: a larger fix round.
- Ruling 47: the restore schema check compares the full sorted rows of sqlite_master (type, name, tbl_name, sql) EXACTLY against the reference built by the same binary (migrations 1..v in memory), refuses duplicates, and keeps the explicit refusal of any trigger or view as a separate first check (defense in depth); no text normalization. A backup whose schema text differs only because another SQLite version wrote it is refused with a message telling the operator to restore it with the tool version that made it — cost: cross-version restores may need the matching tool version.
- Ruling 48: the binary refuses to start when schema_migrations holds a version newer than it knows (clear message: "this database was updated by a newer version; run that version or restore a backup") — an older binary on a newer schema risks silent damage — cost: none.
- Ruling 49: this is the last task, so the reviewer's Minor items 1–8 (CI pinning/permissions, SECRET_KEY on docker-run update, nginx note, path-proxy note, arm64 wording, buildx command, moving machines, caddy tag pin) are folded into this fix round instead of a later wave — cost: a larger round.
- Ruling 50: one final fix wave = the Critical (a NUL stripping + caps, b per-event isolation of data errors, c Postgres test) + open items 1–4 + Minors 1 (spike excludes ignored issues), 2 (events-per-minute editable by admins in Edit project), 3 (document the byte exposure; no new budget), 4 (disk advice), 5 (remove/mark test-only exports; fix CLAUDE.md advice). Minor 6 (splitting restore.go/sourcemaps files, CLAUDE.md line length) is deferred — a refactor at hand-over adds risk for no behavior change.
