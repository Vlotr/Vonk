# Monitoring Tool v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the self-hosted monitoring tool from the concept: one Go binary that pretends to be Sentry (errors) and PostHog (page views, events), with a React dashboard that matches the five designs, shipped as one small multi-arch container.

**Architecture:** One Go process. Ingest handlers parse SDK traffic and push items onto a bounded queue; a single batch writer persists them to SQLite (WAL) or, optionally, Postgres. Background jobs build hourly summaries, send alerts and enforce retention. The embedded React SPA reads a JSON API under `/ui/api/`; that API reads issues, events and hourly summaries, never raw pageviews.

**Tech Stack:** Go 1.27 (stdlib `net/http` routing, `log/slog`, `embed`, `database/sql`), `modernc.org/sqlite` (no CGO), `golang.org/x/crypto` (argon2id), `pgx/v5` stdlib driver (Task 11 only), React 19 + Vite + TypeScript + react-router, Vitest, Playwright, Docker buildx.

**Spec:** `concept-monitoring-tool.md` (Dutch). Designs: `Monitoring dashboard-png/All projects.png`, `Issues.png`, `Issue detail.png`, `Pages.png`, `Settings.png` (the PDF holds the same five screens). Per-phase intent and user-facing wording: `claude-code-prompt.md`.

## Global Constraints

Copied from the spec; every task implicitly includes these.

- Backend Go; dashboard React with Vite, built into the Go binary. Everything (backend, dashboard, background jobs) in one image.
- No extra services: no Postgres, Redis or queue needed. Postgres is optional via `DATABASE_URL`.
- Default database: SQLite in WAL mode, pure Go driver, no CGO.
- Image for x86 (amd64) and ARM (arm64); expected image size about 20 to 30 MB.
- The tool speaks plain HTTP; HTTPS comes from a reverse proxy (Caddy example in the docs). Default port 8000.
- Settings: `SECRET_KEY` (required), `BASE_URL` (required), `DATABASE_URL` (optional, Postgres instead of SQLite), `MAIL_URL` (optional, SMTP; without it notifications go only via Slack). All data lives on one volume at `/data`.
- Retention per project: 30 days, 90 days, 180 days, 1 year or unlimited. Default 90 days. Old data is deleted automatically.
- Sentry: `POST /api/<project-id>/envelope/`, authenticated by the DSN key; support gzip compression and rate-limit headers. Source-map upload API arrives in version 2 (Task 10).
- PostHog: `api_host` points at us. Endpoints `/i/v0/e/`, `/batch/` and `/flags/?v=2`; flags return an empty list.
- We build no SDKs of our own. Laravel errors arrive only via the Sentry SDK.
- Fingerprint = error type + the top lines of the stack trace; equal fingerprints become one issue with a counter.
- Issue status: open, resolved or ignored. A resolved issue that receives a new event reopens.
- Users: invite by link; no Google/GitHub login. Roles admin and member. Members see only projects they have access to. The first user is created via the web page; registration closes afterwards. Forgot password: reset by mail; without mail an admin resets a member in Settings; an admin resets themselves with a server command.
- Notifications per project, each kind on/off: new issue, returning issue, spike (setting: the threshold), summary (daily, weekly or monthly). Via Slack, and via mail when `MAIL_URL` is set. Admins are notified when the tool itself has a problem, such as a full disk.
- Time on page = difference between pageview and pageleave. Without a pageleave the visit does not count in the average and is marked "user left the page". Known bots (by user agent) are excluded from statistics but counted separately.
- Privacy: do not store IP addresses. Filter passwords, tokens and cookies out of error data before storing. Delete-on-request removes all data of one user id.
- Health: a `/health` endpoint, a status page in Settings, and an alert when something is wrong (e.g. disk full).
- Database updates run at startup; a backup is made automatically before them.
- Write events in batches; build hourly summaries (views and time per page); the dashboard reads only those summaries.
- UI copy is English and matches the designs. The tool name is not decided: show `[Tool name]`, defined in exactly one place.

## Project Conventions (decided here, used by every task)

- Go module `monitor`; binary `monitor` in `cmd/monitor`. Subcommands: `serve` (default), `healthcheck`, `project create`, `admin reset-password`, later `restore`, `delete-user-data`.
- Package layout: `internal/config`, `internal/store` (DB, migrations, queries), `internal/sentry` (envelope, event model, fingerprint), `internal/posthog`, `internal/scrub`, `internal/ingest` (HTTP handlers, rate limit, CORS, queue + batch writer), `internal/issues`, `internal/api` (dashboard JSON API), `internal/auth`, `internal/mail`, `internal/alerts`, `internal/jobs`, `internal/routes` (URL → route), `internal/bots`, `internal/web` (embedded SPA). Frontend in `web/`. Examples in `examples/`. Playwright in `e2e/`.
- Extra env vars allowed beyond the spec (all optional): `ADDR` (default `:8000`), `DATA_DIR` (default `/data`), `LOG_LEVEL`, `TZ` (schedules), `DEV_BASIC_AUTH` (Tasks 1–4 only, removed in Task 5).
- Times in the DB are unix milliseconds (`BIGINT`); JSON uses RFC 3339. JSON payloads are `TEXT`. SQL stays in the subset SQLite and Postgres share; migrations live per dialect in `internal/store/migrations/<dialect>/NNNN_name.sql`, embedded, applied in order, tracked in `schema_migrations`.
- Dashboard API under `/ui/api/`, camelCase JSON, errors as `{"error":"..."}`. Missing access and missing objects both return 404.
- Frontend: plain CSS with design tokens as CSS variables in `web/src/styles/tokens.css`, CSS modules per component, no UI kit, no chart library (bars are divs/SVG). Fonts bundled via `@fontsource` (no runtime CDN calls). Light theme only, as designed. Data refresh by polling every 60 s.
- `make dev` (Go + Vite with proxy), `make test` (`go vet`, `go test -race ./...`, web typecheck + Vitest), `make e2e` (Playwright), `make build` (web build → embedded binary in `bin/`), `make docker`.
- Every judgment call an implementer makes goes as one line in `docs/decisions.md`. `CLAUDE.md` holds build/test/run commands and these conventions, updated by each task that changes them.
- Small conventional commits on branch `build/v1`, each ending with the trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push; no remote exists.

## Review Focus

1. **Malformed or unexpected SDK traffic** (truncated envelopes, unknown item types, oversized bodies, new SDK fields): ingest answers 4xx or 200-and-ignore, never 5xx, never panics, never blocks the writer. Pinned by `FuzzParseEnvelope` and handler tests in Task 2, `FuzzParsePosthogBody` in Task 7.
2. **Duplicate, late and out-of-order data** (SDK retries with the same `event_id`, future timestamps, `$pageleave` arriving before its `$pageview`): one row per event id, clamped timestamps, durations paired regardless of arrival order. Pinned in Task 2 (`TestWriter_DedupesEventID`, `TestWriter_ClampsFutureTimestamp`) and Task 7 (`TestDurations_OutOfOrder`).
3. **Access leakage for members**: a member reaching another project through an id in a URL, search, overview aggregates or user activity gets 404 and sees nothing. Pinned by `TestAccessMatrix` in Task 5 and extended by Tasks 8, 9 and 12 for their routes.
4. **Sensitive data in nested places** (headers, cookies, query strings inside URLs, breadcrumbs, extra/contexts, form bodies, frame vars, PostHog properties): filtered before storage; IP never stored. Pinned by `TestScrub_*` in Task 2 and `TestPosthog_ScrubsProperties` in Task 7.
5. **Bursts and a busy SQLite** (thousands of events per minute, slow disk): ingest stays fast, the queue is bounded and answers 429 with `Retry-After` when full, and no `database is locked` error reaches a client or the log as an unhandled failure. Pinned by `TestQueueFull_Returns429` and `TestIngest_ConcurrentLoad` in Task 2 and the perf test in Task 7.
